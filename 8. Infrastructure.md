## Model, Compute, and Tooling Strategy

This document converts the research program into a practical model and infrastructure strategy for a consumer workstation, currently assumed to include an NVIDIA RTX 3060 with 12 GB of VRAM.

The central constraint is not simply fitting the largest possible model. It is preserving the ability to:

- run many repeated trials;
- inspect and intervene on hidden states;
- compare matched model variants;
- train small adapters or recurrent modules;
- reproduce results after software changes;
- fail cheaply before committing to expensive training.

The project should optimize for **scientific leverage per unit of compute**, not parameter count.

1. **Ollama for speed.** Build and validate the Level 1 harness with the models already installed.
2. **A 2–4B white-box transformer for science.** Use it to establish observer controls and activation interventions.
3. **RecurrentGemma 2B as the first native recurrent comparison**, unless state access proves impractical.
4. **A small recurrent adapter rather than a large fine-tune** as the first trained bridge.
5. **A custom sub-billion-parameter organism** for Level 3 developmental experiments.
6. Use larger 7–9B models as replication targets, not as the place every idea must first work.
# 1. Three execution modes

Use three deliberately separated execution modes.

## Mode A — Behavioral scouting

**Default backend:** Ollama or another simple local inference server.

Use it for:

- prompt and task prototyping;
- Level 0 and early Level 1 behavioral comparisons;
- identifying gross floor/ceiling effects;
- testing structured state formats;
- testing whether the model can reliably obey response constraints;
- collecting cheap pilot data across several models;
- building the event-loop and storage infrastructure before white-box work.

Advantages:

- low setup friction;
- existing quantized model library;
- stable API;
- easy switching among models;
- separate thinking/reasoning fields and log probabilities for supported models;
- useful for running many ordinary generations.

Limitations:

- no general access to arbitrary internal activations;
- insufficient for causal hidden-state interventions;
- model templates and quantization may obscure exact comparisons;
- server updates may silently change behavior unless versioned.

**Rule:** An effect found only in Mode A is a behavioral observation, not a mechanistic result.

## Mode B — White-box inference and intervention

**Default stack:** Python + PyTorch + Hugging Face Transformers + NNsight or explicit forward hooks.

Use it for:

- activation logging;
- recurrent-state extraction;
- state reset, swap, and patching;
- layer-wise probing;
- causal ablation;
- norm-matched controls;
- gradient-based analysis;
- matched-precision comparisons;
- testing whether a scaffolded result survives direct manipulation.

Hugging Face models can return layer hidden states and generation scores. NNsight provides a higher-level interface for reading and modifying activations during a model forward pass. Direct PyTorch hooks remain a useful fallback for unsupported architectures.

**Rule:** Any claim involving latent state, privileged access, recurrence, workspace, or mechanism must ultimately pass through Mode B or an equally transparent white-box setup.

## Mode C — Training and development

**Default stack:** PyTorch + Transformers/custom modules + Accelerate + PEFT where applicable.

Use it for:

- LoRA/QLoRA experiments;
- recurrent adapters around frozen backbones;
- monitor or state-interface heads;
- small from-scratch recurrent organisms;
- curriculum experiments;
- continual or online learning;
- developmental twins and controlled training histories.

Training should begin with small models and narrow modules. The program should not start by fine-tuning an 8–12B model on a broad synthetic curriculum.

# 2. Model roles, not one “best model”

The program needs a portfolio of model roles.

| Role | Purpose | Preferred properties | Example candidates |
|---|---|---|---|
| **Cheap behavioral scout** | validate task and data pipeline | 1–4B, fast, strong instruction following | small Gemma/Qwen/Llama-class instruct model |
| **Matched base/instruct pair** | isolate post-training effects | same family and size, both checkpoints available | Qwen or Gemma base/instruct pair |
| **Conventional transformer control** | compare recurrence against ordinary attention | good white-box support, manageable size | 2–4B decoder transformer |
| **Native recurrent model** | direct hidden-state continuity | exposed recurrent state, base and tuned variants desirable | RecurrentGemma, RWKV, Mamba-family model |
| **Adapter substrate** | train a persistent state interface cheaply | frozen backbone, stable hidden size, permissive license | 1–4B transformer or recurrent LM |
| **Tiny organism backbone** | train from birth | 10M–500M initially, simple and inspectable | custom GRU/SSM/looped transformer |
| **Cross-family replication model** | test generality | different tokenizer/training/architecture | model family not used in discovery |

No model should be assigned more scientific meaning simply because it is larger.

# 3. Recommended model sequence

## Phase 1 — use what is already installed

Begin with the models already running reliably in Ollama. This maximizes speed of task development.

For each local model, record:

- exact Ollama tag;
- parameter count if known;
- quantization;
- base versus instruct/chat status;
- chat template;
- whether a reasoning mode is active;
- context length actually used;
- model file digest;
- Ollama version.

Do not compare “Gemma” with “Qwen” as if model family were a single variable. Treat early cross-family differences as scouting observations.

## Phase 2 — establish one matched pair

Select one model family with:

- a base checkpoint;
- a post-trained checkpoint;
- white-box Transformers support;
- a size that can be run repeatedly on the local GPU;
- a license compatible with publication and derived adapters.

The first matched pair should ideally be 2–4B for white-box work. An 8B quantized model can remain a behavioral validation target.

The central comparison is:

```text
same family + same nominal size + same precision
base model versus post-trained model
```

This is much more interpretable than:

```text
small Gemma versus large Qwen
```

## Phase 3 — native recurrence

Bring up one open recurrent or hybrid model.

### RecurrentGemma

Why it is attractive:

- fixed-size recurrent state;
- local attention plus recurrence;
- pretrained and instruction-tuned variants;
- 2B and 9B model families;
- direct connection to the Gemma ecosystem.

The 2B variant is the default first native recurrent organism for a 12 GB GPU. The 9B version may be usable in aggressive quantization for inference, but intervention and training work will be substantially harder.

### RWKV

Why it is attractive:

- recurrent inference formulation;
- explicit state carried token by token;
- mature open ecosystem;
- state can in principle be serialized, reset, copied, and swapped.

Risks:

- version-specific implementations;
- tooling is less standardized than Transformers;
- instruction-tuned and base checkpoints may differ in more than one way.

### Mamba and related SSMs

Why they are attractive:

- compact recurrent state;
- selective state updates;
- strong fit with state-dynamics analysis;
- conceptually clean comparison with attention-based memory.

Risks:

- hidden-state semantics differ from transformer residual streams;
- some available language checkpoints are not matched to strong transformer controls;
- tooling and quantization support vary.

### Recurrent-depth and latent-recurrent transformers

These are important later because they separate multiple forms of recurrence:

- recurrence across **depth**;
- recurrence across **token positions**;
- recurrence across **real/environmental time**;
- recurrence of a **privileged workspace/self-state**.

Do not treat them as interchangeable.

## Phase 4 — custom recurrent adapter

After the native recurrent model experiments identify useful measurements, add a small recurrent module to a frozen backbone.

A minimal form is:

\[
z_{t+1} = \text{GRU}(z_t, P h_t + E(o_t, g_t))
\]

and:

\[
\tilde{h}_t = h_t + Q z_t
\]

where:

- `h_t` is a selected backbone representation;
- `P` compresses it into the recurrent-state interface;
- `z_t` is the persistent latent state;
- `E` embeds observations and endogenous variables;
- `Q` writes recurrent state back into the backbone.

Start with a low-dimensional state such as 128–1024 values, not a full residual stream.

# 4. What fits on 12 GB VRAM

Exact memory depends on architecture, context length, batch size, kernels, precision, and whether gradients are stored. Treat the following as planning bands, not guarantees.

## Inference planning bands

| Model size | Approximate practical use on 12 GB | Research role |
|---:|---|---|
| **<1B** | easy in FP16/BF16; large batches possible | harness tests, from-scratch controls |
| **1–3B** | comfortable white-box inference; limited training possible | primary mechanistic development |
| **4–5B** | white-box inference often feasible with care; quantization useful | stronger validation |
| **7–9B** | quantized inference usually practical; FP16/BF16 weights alone exceed 12 GB | behavioral replication, selected interventions with offload |
| **>10B** | heavy quantization/offload; slow and difficult for activation work | not a default local experimental substrate |

## Training planning bands

| Training target | Feasibility |
|---|---|
| Tiny model from scratch, 10M–300M | high |
| Small recurrent adapter on frozen 1–4B backbone | high–medium |
| LoRA/QLoRA on 2–4B model | medium–high |
| QLoRA on 7–9B model | possible but constrained and slow |
| Full fine-tuning 2B+ | generally not the right local first move |
| Foundation pretraining at multi-billion scale | not local-project territory |

The practical strategy is:

> **Develop the science at 0.1–3B; validate behavior at 4–9B; scale only after a discriminative effect survives.**

# 5. Precision and quantization policy

Quantization is useful, but it can change the very geometry we want to measure.

## Phase-specific policy

### Behavioral scouting

- Q4/Q5/Q8 is acceptable.
- Log quantization explicitly.
- Do not infer hidden-state geometry from Ollama behavior.

### White-box activation studies

Preferred order:

1. BF16 or FP16;
2. 8-bit weights with activation precision documented;
3. 4-bit weights only after a precision-sensitivity check.

### Adapter training

- QLoRA is acceptable for early feasibility work.
- Re-run the strongest effect in a higher-precision small model.
- Never compare a BF16 base model to a Q4 instruct model and attribute the difference to post-training.

## Minimum sensitivity test

For each promoted mechanistic experiment, compare at least two available precision settings on a manageable subset and report:

- behavioral effect direction;
- effect magnitude;
- activation cosine similarity;
- intervention dose-response;
- state trajectory stability;
- false-positive rate.

A result that reverses with quantization remains exploratory.

# 6. Recommended Python stack

## Core

- Python 3.11 or 3.12;
- PyTorch;
- Hugging Face Transformers;
- Accelerate;
- Safetensors;
- Tokenizers;
- Datasets.

## Intervention and interpretability

- NNsight where architecture support is good;
- PyTorch forward/pre-forward hooks as a fallback;
- TransformerLens for supported conventional architectures where useful;
- scikit-learn for probes and classifiers;
- NumPy/SciPy for linear algebra and signal analysis.

## Training

- PEFT for LoRA-style modules;
- bitsandbytes where supported for quantized training;
- TRL only when an RL/preference-training experiment is specifically justified;
- custom PyTorch training loops for the small organism.

## Analysis

- Polars or pandas for run tables;
- DuckDB for querying large JSONL/Parquet collections;
- statsmodels and/or PyMC for confirmatory models;
- matplotlib for figures;
- networkx for causal and transition graphs;
- scikit-learn for clustering, CCA, PCA, and calibration utilities.

## Experiment configuration

Choose one:

- Hydra/OmegaConf;
- Pydantic settings + YAML;
- simple typed dataclasses + TOML.

The key is that every run configuration becomes an immutable artifact.

## Environment management

Use a lockable environment manager such as `uv`, Conda, or Poetry. Commit:

- lock file;
- CUDA/PyTorch versions;
- GPU driver metadata;
- package snapshot;
- container definition later if external replication is planned.

# 7. Backend abstraction

The experiment code should not depend directly on Ollama or Transformers.

Define a common interface conceptually similar to:

```python
class CognitiveBackend(Protocol):
    def initialize(self, config: ModelConfig) -> ModelHandle: ...
    def run(self, request: RunRequest) -> RunResult: ...
    def score(self, request: ScoreRequest) -> ScoreResult: ...
    def snapshot_state(self) -> StateArtifact | None: ...
    def restore_state(self, state: StateArtifact) -> None: ...
    def intervene(self, spec: InterventionSpec) -> ContextManager: ...
    def close(self) -> None: ...
```

Implementations:

- `OllamaBackend`;
- `TransformersBackend`;
- `NNsightBackend`;
- `RecurrentGemmaBackend`;
- `RWKVBackend`;
- `CustomOrganismBackend`.

The interface should expose capability flags rather than pretending all backends support all operations.

```yaml
capabilities:
  token_logprobs: true
  hidden_states: false
  state_snapshot: false
  activation_intervention: false
  gradient_access: false
  online_learning: false
```

This prevents Level 1 implementation choices from contaminating Level 2.

# 8. Model-selection scorecard

Score candidate models from 0–3 on each dimension.

| Dimension | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| Local fit | unusable | heavy offload | workable | comfortable |
| Base/instruct match | none | imperfect | good | strong controlled lineage |
| White-box support | poor | custom work | adequate | excellent |
| State accessibility | none | indirect | exposed | designed for intervention |
| Training feasibility | impossible | difficult | adapter only | easy |
| License/release | restrictive | unclear | acceptable | permissive/clear |
| Existing literature | absent | sparse | useful | direct target literature |
| Cross-level utility | one-off | limited | multiple sprints | core substrate |

Do not select only by the total. A model with excellent behavioral performance but no state interface may be a useful validation model and a poor mechanistic organism.

# 9. Compute-budget gates

Every experiment card should estimate:

- number of items;
- conditions;
- seeds/samples per item;
- average input/output tokens;
- intervention layers/strengths;
- approximate GPU-hours;
- storage footprint;
- analysis time.

## Budget bands

### Band S — Scout

- under 2 GPU-hours;
- under 100 MB of artifacts;
- one or two models;
- designed to kill bad tasks quickly.

### Band E — Establish

- 2–20 GPU-hours;
- held-out items and multiple prompts/seeds;
- basic observer and replay controls.

### Band C — Causal

- 10–100 GPU-hours depending on layer sweeps;
- hidden-state intervention;
- matched controls;
- state logging may dominate storage.

### Band T — Training

- explicit wall-clock and energy ceiling;
- checkpoint frequency;
- early-stopping metric;
- predeclared stop condition;
- no training run without a baseline that the new module must beat.

### Band R — Replication

- frozen configuration;
- independent architecture/model family;
- separate analysis output;
- no ad hoc prompt changes after seeing results.

A Band T run should not be approved merely because the code is ready. It requires a scientific gate from prior experiments.

# 10. Storage strategy for hidden-state work

Full activations become enormous quickly.

Default hierarchy:

1. Save raw outputs, logits for scored options, and state hashes for every run.
2. Save selected layer/token summaries for exploratory runs.
3. Save full activations only for a predeclared subset.
4. Store derived features in Parquet/Zarr.
5. Keep a reproducible extraction script so derived summaries can be regenerated.
6. Compress state snapshots and deduplicate identical artifacts by hash.

Possible summaries:

- norm;
- mean/variance;
- selected token positions;
- PCA projection;
- probe logits;
- cosine similarities to registered directions;
- effective rank;
- autocorrelation features;
- state-difference vector between branches.

Never throw away the linkage between a derived vector and the exact run/model/token/layer that produced it.

# 11. Determinism and replay

PyTorch warns that exact reproducibility is not guaranteed across releases, platforms, and hardware. Therefore the project needs two concepts:

- **within-environment determinism:** repeated run on the same locked environment;
- **scientific robustness:** conclusions that survive expected numerical and sampling variation.

For deterministic tests:

- set Python, NumPy, and PyTorch seeds;
- disable sampling or use fixed generators;
- place models in evaluation mode;
- record deterministic-algorithm settings;
- record CUDA/cuDNN versions;
- hash model files and inputs;
- compare token IDs, logits, and state tensors with tolerances;
- record operations that cannot be made deterministic.

Do not force every exploratory run into the slowest deterministic mode. Instead maintain a dedicated replay test suite and make stochasticity explicit elsewhere.
